# Voice eval 2026-11-11

The five phone screens' voice test sets (Inbox, Work item, Backlog, Features, Retro) were run through the real Qwen3 and Parakeet files on a laptop CPU, then scored with the phone's own `parseModelOutput` and `copyNoteSpan` (`tools/voice-eval/score.ts`). This is the first run on the real model files (SHIP-1204, wave 3 of SHIP-916).

- **Date:** 2026-11-11 (UTC). Run files: `~/.cache/shiplean-voice/eval-out/runs/2026-11-11/`.
- **Host:** AMD Ryzen 7 7730U, 8 threads, 7 GB RAM (WSL2), glibc 2.31.
- **Model server:** `llama-server` from conda-forge llama.cpp build 10333 (`tools/voice-eval/llama-server-conda.sh`, SHIP-1322). The prebuilt b10256 in `eval-models.manifest` needs glibc 2.34. 10333 is the nearest conda-forge build that has b10256's Qwen3 chat parser.
- **Request:** the pack's GBNF grammar, `temperature: 0`, thinking off (RUN.md).

## Headline

- **Neither model gets 90 % on most actions.** Right action is about 74 % for both models in the text tier. Right args is about 49 %. Of 45 actions, 31 are flagged for each model in the text tier. In the audio tier, 29 of 39 are flagged.
- **4B adds nothing on these numbers.** On the same 135 rows, 4B scores 75 % right action and 48 % right args. 1.7B scores 74 % and 51 %. 4B is about three times slower and its download is 2.3× bigger (2.5 GB against 1.1 GB).
- **Exact note was not measured at all.** All 73 test-set rows that expect a note fail the exporter's check, so no note action reached either model (see Rejected rows).
- **Parakeet doesn't write keys as keys.** Only 1 of the 34 keys that were said came out in the transcript as `SHIP-n`. It writes "ship 743", or spells the number out ("ship nine hundred six", once "chip seven hundred forty three"), even with the keys in its hotwords.
- **Much of the "right args" gap comes from the scoring.** The scorer requires the arguments to be exactly equal. The models often add optional arguments the row left out (`"all": false`, `"board": true`, `"feature": "SHIP-906"`, `"person"`, `"mention"`). They also give a retro point's real title where the row expects the words that were said ("the build point"). If the expected arguments must match and extra ones are allowed, text right args rises from 49 % to 60 %.

The times are seconds per command on this CPU with 8 threads. They count the model and, in the audio tier, speech recognition. They leave out speech synthesis.

**CPU times on this laptop aren't phone times.** Use them to compare models and screens, not as the delay a phone will show. The phone targets (under 2 s on an S24 or iPhone, under 5 s on an S22) are checked only by the device run.

- The slowest 1.7B rows were run-on replies. Each over-60 s row repeated a call or listed one call per decision or item, with a median reply of about 700 characters against 79 for all rows. The grammar allows any number of calls, so a repeating reply only ends at the token limit.
- The first row of each run file is slow (16–148 s) because the prompt is processed cold. The worst is the 148 s first row of the audio Inbox run, which was also a run-on reply.
- 4B on Features was the slowest run: median 77 s a row and 140 s per 100 reply characters, against 45–70 s on the other 4B screens. A WSL crash interrupted it partway, and it was resumed (rows already in the file are skipped). So the run includes a second cold load, and the host may have been under memory pressure around the crash. Read the 4B Features and Retro times as an upper bound.
- 4B's p90 (109 s) comes from ordinary replies, not run-ons: 42 of 135 rows took over 60 s with a median reply of 80 characters. 4B is simply about 3–4× slower per token on this CPU.

## What was sampled, and why

| Run               | Rows                                                                                | How chosen                                     |
| ----------------- | ----------------------------------------------------------------------------------- | ---------------------------------------------- |
| Text, Qwen3 1.7B  | 172 (every exported row): Inbox 31, Work item 37, Backlog 38, Features 33, Retro 33 | all                                            |
| Audio, Qwen3 1.7B | 90: Inbox 12, Work item 20, Backlog 22, Features 20, Retro 16                       | `--sample <2 × the screen's actions> --seed 1` |
| Text, Qwen3 4B    | 135: Inbox 18, Work item 30, Backlog 33, Features 30, Retro 24                      | `--sample <3 × the screen's actions> --seed 1` |

The brief's sizing rule says to run 4B on every row only if 2.5 × the 1.7B time per row comes to under 60 minutes. The 1.7B rows took 16–116 s each. At about 27 s a row over the early chunks, 172 rows at 2.5× projects to about 3 hours, so 4B was sampled at 3 rows per action. Over the full run, the 1.7B median was 11.5 s; the early chunks were Inbox and Backlog, the slowest screens. 4B audio is out of scope. The audio tier synthesises each utterance with the Piper voice `en_US amy low`, transcribes it with Parakeet using the screen's hotwords (from the phone's `toHotwords`), and then sends the transcript to 1.7B.

## What to change

None of these were changed here. The test-set rows, specs and harness belong to their own tasks.

1. **Note rows (all five specs, or the exporter, VE4a).** No row has a `noteSpan`. The specs write the note as the row's `note` and put a placeholder such as `"note": "x"` in the arguments, but the exporter takes the note only from `calls[i].noteSpan` through `copyNoteSpan`. So every note action (answer, reply, add_note, set_status, add_point, add_item, discuss…) fails the check and goes unmeasured. One side has to change: either the rows carry a `noteSpan` over the utterance's words, or the exporter works out the span from the row's `note`. Then rerun the text tier on those 73 rows.
2. **Optional arguments (scoring or rows).** Decide whether a call that adds an optional argument with its default or an obvious value counts as right: `"all": false` on Inbox approve, `"board": true/false` and `"feature"` on Features filter_open and ask_status, `"person"` and `"mention"` on Inbox seen. If yes, the scorer should compare only the expected keys plus any non-default extras. If no, the prompt should tell the model to leave out arguments that weren't said. This one choice moves text right args from 49 % to 60 %.
3. **Retro point references.** The rows expect `point` to be the words that were said ("the build point", "the signing key point"). Both models give the point's title from the context instead ("The S22 build took 40 minutes"). Decide which one the phone resolves. Then fix either the rows (support, make_action, add_to_action, not_needed, answer_merge) or the prompt's rule for `point`.
4. **Keys in speech.** Parakeet writes `SHIP-906` as "ship 906" or "ship nine hundred six" (33 of 34 keys), so the `SHIP-n` hotwords aren't working as the phone sends them. The model often recovers the key anyway, but audio right args is 8 points lower than text. Options: hotwords in their spoken form, or turning "ship <number or number words>" back into `SHIP-<number>` before the prompt. 1.7B twice wrote a decision number as `1001001001001001`, and 4B once wrote `1234567890123456`. The grammar's integer rule has no length limit.
5. **Run-on replies.** 1.7B sometimes repeats a call or lists one call per decision or item ("approve all" became eight `discuss` calls). Its slowest rows are all of this kind. A limit on calls per reply in the grammar (most screens need at most 2 or 3) would cut both the errors and the worst latency.
6. **Actions confused with each other:** Inbox approve and chooseDecision against `discuss`; Inbox stillTrue against `status`; Work item approve_decision against `confirm_status` and `discuss_decision`; Backlog filter against `ask`/`open`; Backlog switch_level against `filter`; Retro show against `add_point`; Features set_state against `move_rank`/`set_health`. Their action descriptions in the specs need sharper wording or more examples.
7. **4B returns `[]` on the Work item screen.** It does this for set_state, confirm_status, approve_decision and set_health, 12 rows in all, where 1.7B at least gives a call. This is worth a look at the Work item prompt.
8. **Thin rows.** The exporter warns about 47 screen actions with fewer than 5 rows. 17 of them have none left after the note rows were rejected, and 30 have 1–4 rows. Many figures above rest on 1–4 rows, so one row moves a share by 25–100 points. The brief expected at least 3 rows per action from each spec.
9. **4B: not worth its extra download on these numbers.** Row for row it is level with 1.7B (75 % against 74 % right action, 48 % against 51 % right args). It costs about 3× the time per command on this CPU (median 32 s against 11.5 s) and 1.4 GB more to download. Look at it again once items 1–3 are settled, because the scoring currently hides the differences that matter.

## Harness breaks found

- **The RUN.md export command no longer runs** once the real screens are registered. `node --import ./tools/voice-eval/ts-hooks.mjs … export.ts` fails with `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX` at `src/ShipLean.Core.Client/src/api/client.ts:55`, a TypeScript parameter property. Node's strip-only mode can't run it, and the screens' specs reach `@shiplean/core`. Adding `--experimental-transform-types` makes it work. The score command still runs as written. RUN.md (VE4a's file) needs the flag, or the import has to go.
- **The note check rejects every note row** (item 1 above). The exporter's check is right for the contract it states. The test sets were written to another one.
- **The scorer only reports exact matches** (item 2). The scorer is working as built, but its single strict figure hides how much of the gap is optional arguments.
